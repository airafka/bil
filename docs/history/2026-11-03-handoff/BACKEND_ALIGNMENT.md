## Активные тарифы и фиксация при создании заявки · 03.11.2026

V12 добавляет complex_service_tariff.active boolean NOT NULL DEFAULT true; все существовавшие тарифы активны. Прежний UNIQUE по услуге/договору заменён частичным уникальным индексом по услуге + клиенту + договору WHERE active. Неактивные записи сохраняются отдельно. Создание тарифа больше не перезаписывает коэффициент существующего: если есть активный тариф с теми же ключами, возвращается 409 ACTIVE_TARIFF_EXISTS (в том числе при создании неактивной строки). Включение старого тарифа при наличии другого активного также запрещено. Создание/редактирование сериализованы блокировкой услуги; индекс дополнительно защищает БД от дублей.

UI «Активный»: checkbox только для просмотра в таблице, изменение исключительно через форму редактирования с сохранением/отменой. Новый тариф по умолчанию активен. Редактирование и удаление адресуются по tariffId, поскольку на один договор теперь возможны несколько исторических записей. PUT /api/complex-services/{id}/tariffs создаёт запись; PUT /api/complex-services/{id}/tariffs/{tariffId} редактирует коэффициент/active; DELETE по тому же пути удаляет только выбранную запись. Клиент/договор при редактировании неизменяемы. Использованный в заявке или расчётах тариф удалить нельзя; его можно отключить. Отсутствующий active в старом запросе создания означает true, при редактировании сохраняет прежнее состояние.

По явному решению пользователя V13 фиксирует тарифы ПРИ СОЗДАНИИ новой comprehensive_service_order. Требуются ВСЕ ТРИ активных тарифа для выбранных клиента и договора: A_WAGON (менее 40 КТК), A_TRAIN (40 КТК и более), B_AUTO_RETURN (возврат). В снимок записываются все три; подходящая первоначальная разновидность определяется по фактическому числу принятых уникальных КТК. Создание без любого из них откатывается целиком (ACTIVE_TARIFFS_REQUIRED), накладные остаются свободными. Проверка и снимок выполняются в общей транзакции с блокировкой тарифов и базовых цен.

Начисления по новым заявкам используют только этот снимок, даже после отключения/редактирования/замены тарифа и изменения базовой цены услуги. Фиксируются обе разновидности первоначальной услуги и тариф возврата. Повторное выполнение не создаёт повторных начислений.

## Ручная накладная и интеграционный обработчик

Граф хранения одинаков в поддерживаемой части:

```
waybill → waybill_railway_carriage → waybill_container → waybill_zpu
       → waybill_product
```

Создание накладной, состава, грузов и ЗПУ выполняется одной транзакцией. Станции и плательщик находятся/создаются по доступным MVP ключам; вагоны, КТК и ЕТСНГ выбираются из существующих справочников. Интеграция получает полные реквизиты и умеет создавать/обновлять их; ручная форма не подменяет эти реквизиты отсутствующими данными.

По решению пользователя прежнее правило «всегда один груз» заменено правилами validateWaybillDto основной системы: хотя бы один груз обязателен, в том числе для порожней накладной; несколько грузов разрешены только с ровно одним КТК. Не введено равенство суммы масс грузов и нетто КТК: исходный обработчик хранит их независимо.

Форма передаёт products[] с etsngCodeId, weight, signDanger. Массы грузов неотрицательны, включая 0 для порожней накладной. Нетто каждого КТК можно ввести явно; первоначальная подсказка — брутто минус справочная тара. Оно сохраняется в net_weight и не изменяется при последующей правке тары. Для прежних запросов с одним etsngCodeId и без netWeight поддержан расчёт в момент создания. Старый запрос совсем без груза теперь отклоняется.

ЗПУ сохраняются отдельными строками, разделители ручного поля — запятая, точка с запятой или перевод строки. Ведущие нули сохраняются. Общий тип выбранной строки КТК записывается в zpu_type каждого ЗПУ. Собственник и признак опасности груза сохраняются текстовыми снимками, как у интеграции.

Один или несколько грузов не размножают строки КТК в реестре и составе поставки. Производный автовывоз сохраняет все положительные строки грузов в shipping_order_container_item; API возвращает cargoItems. Для одного общего груза вес вывоза берётся из зафиксированного нетто соответствующего КТК; для нескольких — из отдельных масс грузов. Повторяющийся КТК с конфликтующим составом выбранных накладных отклоняется. Биллинг остаётся по КТК, а не по строкам груза.

## Подтверждение транспортных заявок через рейс · 03.11.2026

Поставки/вывозы создаются в DRAFT без обязательного рейса и без обязательных плановой даты/грузоотправителя. Подтверждение только POST /api/routes/{id}/confirm: в одной транзакции блокируются рейс и заявки, проверяются все реквизиты, резервируются КТК, заявки и рейс переходят в CONFIRMED. Прямой PATCH статуса транспортной заявки в CONFIRMED запрещён (409 CONFIRM_THROUGH_ROUTE). Пустой/не-DRAFT рейс подтвердить нельзя.

Перед подтверждением поставка требует plan_receiving_date_time и непустого consignor; вывоз требует planned_shipping_date_time. У вывоза в модели есть грузополучатель, поля грузоотправителя нет; новые поля не добавлялись. Ошибка перечисляет номера заявок и недостающие реквизиты; вся операция откатывается, включая резервы/историю КТК. Поля редактируются карандашом во вкладке Основное черновика (в том числе автоматически созданного); PATCH /containers поддерживает optional metadata {plannedAt, consignor} в общей транзакции с реквизитами КТК. После подтверждения правка запрещена.

В карточке транспортной заявки нет Подтвердить, только Выполнить при CONFIRMED. Выполнение сохраняет существующие движения/начисления и автоматически завершает связанный CONFIRMED-рейс, когда все его заявки COMPLETED. Блокировка рейса перед заявкой сериализует конкурентные выполнения; повторное завершение идемпотентно. Данные рейса в карточке заявки перечитываются после выполнения. Статусы комплексной услуги и смены собственника не изменялись.

Справочник: docsforanalytics 2.zip, business-rules/order-statuses.md (путь UI после KIS-4735), route-ui-rules-as-is.md. Использована модель MVP DRAFT/CONFIRMED/COMPLETED, дополнительные статусы основной системы не переносились.
