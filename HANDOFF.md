## Бизнес-правила заявок и услуг

- Статусы: `DRAFT` — «Черновик», `CONFIRMED` — «Подтверждено», `COMPLETED` — «Выполнено».
- Черновик означает, что заявка создана. Подтверждение означает отправку во внешнюю систему. В дальнейшем выполнение должна устанавливать смежная система; в MVP статус меняют вручную.
- Заявка на услугу объединяет два процесса. В интерфейсе показывать **наименования из справочника**, без «Услуга 1/2» и буквенных префиксов.
- Первый процесс: первоначальная поставка и последующий вывоз КТК. Услуга выполнена по КТК только после выполнения заявки на его вывоз. Принятым КТК считается после выполнения первоначальной поставки.
- Второй процесс: возвратная поставка, созданная на основании вывоза. Выполнение определяется выполнением соответствующей заявки на поставку.
- Для КТК «Стандартный 20» заявки на вывоз создаются через выбор КТК; нельзя считать, что вывоз автоматически оформлен на каждый КТК.
- Количество КТК и количество заявок — разные показатели. В первоначальной поставке всегда одна заявка; отдельное количество заявок нужно показывать для вывоза и возвратной поставки.

## Карточка заявки на услугу и дашборд

- Вкладки: «Основное», «Заявки на поставку», «Заявки на вывоз», «Возвратные заявки».
- На «Основное»: клиент, договор, статус, статистика и «Начисления».
- Блок «Начисления» переименован из «Начисления по КТК» и должен отображаться только на вкладке «Основное».
- Дашборд — компактные таблицы с названием услуги и синей шапкой: «Операция», «Показатель», «Всего», «Выполнено».
- Названия операций: «Поставка КТК», «Вывоз КТК»; для возвратной поставки также «Поставка КТК».
- У первоначальной поставки только строка КТК. У вывоза и возвратной поставки сначала «Заявки», затем «КТК».
- «Всего» включает КТК/заявки независимо от выполнения; «Выполнено» — только завершённые. Не путать общее количество с количеством черновиков.
- Блок второй услуги скрыт, пока нет подходящих возвратных заявок.
- Предупреждение «Без заявки на вывоз: N» показывать только при N > 0.
- Пользователь хочет компактный интерфейс без широких пустот и высоких пустых карточек. Не возвращать ранние варианты с огромными цифрами и отступами.

## Собственник КТК независимо от клиента — уточнение 2026-11-02

Обычный client_id заявки на поставку/вывоз не определяет собственника регистра. При создании поставки defaultContainerOwnerId обязателен и выбирается независимо от клиента; неуказанный собственник строки подставляется из этого поля, явный собственник строки имеет приоритет. В черновике можно менять собственника отдельного КТК; изменение общего собственника по умолчанию по ранее принятому правилу обновляет все строки. Смена клиента/транспорта формы не заменяет отдельно выбранного собственника. Старые сохранённые владельцы и данные не переписываются.

При подтверждении поставки container_owner.client_id получает собственника соответствующей строки receiving_order_container (статус EXPECTED). UNLOAD_FINISH переводит КТК в ON_TERMINAL с сохранением собственника регистра. CHANGE_OWNER изменяет собственника регистра; DRAFT/CONFIRMED вывозы получают актуального собственника из container_owner по container_id. Изменение регистра синхронизирует owner_container_id активных вывозов в той же транзакции. Завершённый вывоз хранит собственника на момент LOAD_FINISH и не меняется задним числом.

По отдельному уточнению пользователя возврат допускает ручной выбор собственника. При создании собственник каждого КТК копируется из вывоза: для активного вывоза это актуальный регистр, для завершённого — сохранённый собственник на момент вывоза. ## Уточнение: собственник автоматически меняется только в черновике вывоза — 2026-11-02

Это уточнение заменяет прежнее правило синхронизации DRAFT/CONFIRMED. Только DRAFT получает актуальный собственник из container_owner при его изменении. При подтверждении вывоза owner_container_id фиксируется из регистра; после подтверждения ни CHANGE_OWNER, ни LOAD_FINISH не переписывают это поле. Для CONFIRMED/COMPLETED API показывает сохранённый owner_container_id, а не текущий регистр. Сам container_owner при CHANGE_OWNER меняется независимо от снимка подтверждённого вывоза; выполнение вывоза сохраняет актуального собственника регистра и меняет статус на DEPARTED.

Возврат по умолчанию копирует собственника вывоза: для DRAFT — актуальное значение регистра, для CONFIRMED/COMPLETED — зафиксированное значение заявки. Ручное редактирование собственника черновика возврата остаётся разрешённым.

Проверено: Maven package с тестами; сценарии API+SQL на отдельной копии БД для авто и ЖД, включая два вывоза одного КТК (подтверждённый сохраняет собственника, черновик обновляется), выполнение после CHANGE_OWNER и возврат из подтверждённого вывоза. Контрольные суммы 43 таблиц на копии до сценариев совпали с рабочей БД. Изменения схемы и корректировка существующих данных не требуются; frontend не пересобирается. Резервная копия before-draft-owner-2026-11-02.dump.
