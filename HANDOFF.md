Все шесть мест — создание поставки/вывоза, две карточки, две таблицы услуги — используют стандартный UiSelect из `/api/references/clients`.

`PartyReferences.clientName` проверяет имя по `client`; произвольный текст даёт400 `CARGO_PARTY_CLIENT_NOT_FOUND`. Пустота возможна в черновике, обязательность — при подтверждении рейса. API сохраняет прежние строковые поля. В БД `receiving_order.consignor` остаётся текстом, `shipping_order.consignee_id` — ссылкой на `client_related_entity`: **внешний ключ на client не переносили**.

Клиент договора, собственник, статусы и остальные данные не менялись. Служебные записи получателей скрыты из транспортного справочника; добавление клиента само по себе не означает добавление перевозчика.

### Справочники и боковые формы рейса

### Остальные важные договорённости

- Тарифы фиксируются при создании комплексной заявки; обязательны все3 назначения: <40, >=40, возврат. Не пересчитывать старые начисления при изменении тарифа.
- Подтверждение поставки/вывоза только через рейс; выбранный рейс не обязателен при создании черновика. Даты/отправитель/получатель обязательны при подтверждении.
- Выполнение всех заявок автоматически завершает рейс; комплексная заявка завершается после всех её заявок и распределения исходных КТК в вывозы.
- Возврат можно подготовить до приёмки исходной поставки: собственник из плановой поставки/КТК накладной; для подтверждённого вывоза — зафиксированный собственник.
- Блок начислений в карточке услуги скрыт, пока записей нет.
- Счёт: DRAFT→PAID кнопкой «Оплачен», редактирование карандашом только DRAFT, удаление из строки; защита version от устаревшей вкладки.
- Карточка тарифа одна на тариф, без списка счетов/заявок; ссылки из счетов ведут на неё.
