# Сверка существующего MVP с документацией

Дата: 02.11.2026. Проверен текущий локальный MVP из «Билинг 2.0», активные миграции V1–V6. Рассмотрены 46 физических таблиц и 3 представления, всего 328 полей с учётом представлений; история Flyway не включена в это число. Пропущенные относительно большой системы поля и отсутствующие в MVP процессы сами по себе не считаются ошибками.

**Вывод:** основной каркас моделей совпадает, но полного соответствия логики нет. Воспроизведены две ошибки учёта КТК (A1/A2), ошибка отображения массы (A3) и четыре расхождения существующих полей/проверок (A4–A7). Исправления в код и рабочую БД в рамках этой проверки не вносились.

## Основания и границы

Источник сравнения — предоставленный архив docsforanalytics: физические модели, lifecycle и актуализации сентября–октября. Июльский backend.7z использовался как дополнительный источник, когда он описывает тот же участок. Новые сентябрьские правила не приписываются отсутствующему в июльском архиве коду.

Документация сама обозначает свои модели как реконструкцию по исходникам, а не выгрузку production-БД. Проверенная физическая схема здесь — именно схема MVP. Достоверность текущего production-развёртывания не утверждается.

Изменения, прямо согласованные пользователем, имеют приоритет: ручные события вместо TOS; три статуса транспортных заявок; отдельный comprehensive_service_order; текст owner в накладной и выбор клиента в поставке; собственник вывоза из регистра; массовая замена всех собственников КТК при смене значения по умолчанию в черновике. Они не записаны в дефекты.

Не проверялись отсутствующие функции: WMS/TOS/Datareon HTTP-интеграции, складские товары/партии, permissions и роли, Excel/PDF, отмена заявок, выпуск/оплата счёта, полная библиотека справочников. Поле и поведение, уже представленные в MVP, проверялись, даже если их реализация сокращена.

## Подтверждённые ошибки

### A1 — P1. Накладные и регистр КТК расходятся при добавлении накладной в существующую поставку

В основной модели резервирование учитывает объединение ReceivingOrderContainer и привязанных WaybillContainer. В MVP резервирование читает только receiving_order_container. Эти строки создаются при создании ЖД-поставки, но не при POST /api/waybills с receivingOrderId существующей поставки.

Воспроизведение: создать накладную с КТК 1 → создать поставку → добавить вторую накладную с КТК 2 через receivingOrderId → подтвердить и выполнить поставку. Ответ: две накладные, одна строка receiving_order_container, COMPLETED; в container_owner нет КТК 2. Дополнительно API принял новую накладную в уже выполненную поставку с HTTP 201.

Риск: часть фактически показанного состава поставки не попадает в остатки и историю. Изменение состава после завершения также делает уже зафиксированную приёмку недостоверной.

Рекомендация: один согласованный источник состава для резервирования и завершения либо атомарная синхронизация строк при каждом разрешённом изменении состава; блокировка строки поставки; запрет изменения состава подтверждённой/выполненной поставки. Запрет не выдаётся за доказанное правило всех endpoint основной системы: это необходимая защита согласованности самого MVP.

### A2 — P1. Ранний возврат может сменить собственника без заявки CHANGE_OWNER

Это внутренняя ошибка существующего MVP-процесса «возврат в сток собственника»; отдельный аналог этого комплексного процесса в документации большой системы не установлен.

Воспроизведение: клиент комплексной заявки A, собственник поставки B. Автовывоз создаётся заранее, когда регистра ещё нет, поэтому его owner_container_id пуст. Создать возврат до подтверждения вывоза: он копирует пустого собственника, а правило по умолчанию подставляет A. После фактической приёмки и подтверждения вывоза его собственник правильно становится B, но черновик возврата остаётся с A. Выполнение возврата меняет регистр B → A без service_order.

На копии БД ownerBeforeReturn не равен ownerAfterReturn; новый собственник совпал с клиентом заявки, а не с собственником отправленного КТК.

Рекомендация: для автоматически созданного возврата разрешать собственника по подтверждённому вывозу/регистру перед резервированием или создавать возврат после фиксации владельца вывоза. Нельзя использовать fallback на клиента заявки как молчаливую замену неизвестного владельца возврата. Отдельно сохранить возможность явного пользовательского выбора там, где она предусмотрена.

### A3 — P2. Масса строки груза отображается как брутто всего КТК

Документация различает waybill_product.weight и gross_weight. MVP поддерживает только сохраняемую массу продукта weight, но API создаёт grossWeight суммированием waybill_container.weight и отдаёт одну и ту же сумму каждому продукту. UI выводит её как «Масса брутто, кг».

Воспроизведено: один КТК, брутто 6000 кг; два продукта с массами 600 и 900 кг. В API обе строки получили grossWeight=6000. Если сложить показанные строки, получится 12000 кг; отдельный итог в UI этим тестом не утверждается. Указанные пользователем 600/900 на этой вкладке не показаны.

Рекомендация без переноса отсутствующих атрибутов: показывать существующее product.weight с подписью «Масса груза», а общий брутто КТК — отдельным показателем. Не присваивать массе каждого продукта значение брутто всей накладной и не добавлять gross_weight в БД без отдельного решения.

## Расхождения правил и контрактов

### A4 — P2. Подтверждение пропускает документированные проверки существующих полей

Гружёная автопоставка без даты поступления, рейса, класса опасности и типа ЗПУ создана и подтверждена с HTTP 200. В документации дата и связанный рейс проверяются перед accept/review; известный гружёный КТК требует dangerClass и sealType.

Это подтверждённое различие, но не все исходные проверки следует переносить автоматически: переход CONFIRMED в MVP — согласованная адаптация accept. Требуется определить применимый минимум. В частности, обязательность поля опасности не означает, что каждый груз опасный: для неопасного выбирается запись «Отсутствует».

В рамках проверки не требуются отсутствующие в MVP currency/customsClearance/ISO и прочие поля. Также consignor не приравнивается к shipper: это разные роли, ранее специально разделённые.

### A5 — P2. Порожнему КТК поставки не подставляется класс «Отсутствует»

В receiving-обработчике основной системы empty=true заменяет класс на справочную запись «Отсутствует». В MVP порожняя строка без класса сохраняется с NULL, несмотря на наличие записи code_danger_class=0. Проверено созданием порожнего КТК через API. Явно выбранный класс также не нормализуется по empty.

Рекомендация: если требуется это правило большой системы, применять его на сервере в receiving-create/update, а не только показывать подходящий пункт в UI. Для shipping не утверждается наличие такого же присваивания: проверенный документ не подтверждает его однозначно.

### A6 — P2. Разные значения одного filling_type

Описанный режим неизвестного порожнего КТК автoвывоза называется NONE_CONTAINER. В MVP это VEHICLE_UNNUMBERED и в Java enum, и в DB CHECK, и в UI. Запрос с NONE_CONTAINER отклонён HTTP 400 / INVALID_FILLING_TYPE.

Сам режим уже существует в MVP, поэтому это не запрос на новую функцию, а несоответствие имени существующего значения. Для совместимости потребуется явное сопоставление/переименование с миграцией и проверкой старого API, а не добавление второго независимого режима.

### A7 — P2. etsng_code.code содержит код вместе с наименованием

В документации code — ключ справочника, name — отдельное свойство. В текущем MVP поле code содержит, например, «011005 — Пшеница». Код и название восстанавливаются разделением строки при чтении. Внешний поиск по чистому коду и прямое использование code как кода ЕТСНГ с таким хранением несовместимы.

Внутренний выбор по UUID при этом работает — это семантическое различие поля, не доказательство отказа всех операций MVP. Рекомендация: закрепить раздельный смысл кода и отображаемой подписи. По прежнему ограничению пользователя отсутствующий name не добавлять автоматически; способ сохранения подписи и миграции данных согласовать отдельно.

## Что прошло проверку

- Связь DangerProduct → DangerClass; неизменность текстового signDanger при выборе класса.
- Нетто КТК хранится снимком и остаётся 1500 после изменения справочной тары; текст owner не превращается в клиента по имени; ЗПУ 0001/0023 сохраняют нули.
- Default owner: fallback на клиента, другой клиент по умолчанию, исключение в строке КТК, замена всех строк при фактической смене default, блокировка после подтверждения.
- Регистр: EXPECTED → ON_TERMINAL → RESERVED_OUT → DEPARTED; собственник вывоза берётся из регистра, переданный вручную другой владелец игнорируется; повтор ручного события не дублирует movement.
- Смена собственника: запрет пустого выполнения, сохранность выбора после ошибочного запроса, DRAFT → DONE, сохранение состояния остатка, один outbound, запрет повторного accept.
- История через API: SERVICE_ORDER отображается; полный журнал включает резервирования.
- Рейсы: совместимые направление/транспорт/площадка, сохранение route_id, отклонение повторного назначения уже занятой заявки.

## Собственник КТК независимо от клиента — уточнение 2026-11-02

Обычный client_id заявки на поставку/вывоз не определяет собственника регистра. При создании поставки defaultContainerOwnerId обязателен и выбирается независимо от клиента; неуказанный собственник строки подставляется из этого поля, явный собственник строки имеет приоритет. В черновике можно менять собственника отдельного КТК; изменение общего собственника по умолчанию по ранее принятому правилу обновляет все строки. Смена клиента/транспорта формы не заменяет отдельно выбранного собственника. Старые сохранённые владельцы и данные не переписываются.

При подтверждении поставки container_owner.client_id получает собственника соответствующей строки receiving_order_container (статус EXPECTED). UNLOAD_FINISH переводит КТК в ON_TERMINAL с сохранением собственника регистра. CHANGE_OWNER изменяет собственника регистра; DRAFT/CONFIRMED вывозы получают актуального собственника из container_owner по container_id. Изменение регистра синхронизирует owner_container_id активных вывозов в той же транзакции. Завершённый вывоз хранит собственника на момент LOAD_FINISH и не меняется задним числом.

По отдельному уточнению пользователя возврат допускает ручной выбор собственника. При создании собственник каждого КТК копируется из вывоза: для активного вывоза это актуальный регистр, для завершённого — сохранённый собственник на момент вывоза. Общий default возврата устанавливается по первому КТК; у всех строк сохраняются их собственные значения. Если собственника в вывозе ещё нет (исходная поставка не подтверждена), создание возврата возвращает HTTP 409 RETURN_OWNER_REQUIRED без записи возврата. Подстановка клиента исключена. Ручное изменение владельца в черновике возврата разрешено; при подтверждении такой возврат регистрирует выбранного владельца. Поэтому смена владельца через явно отредактированную входящую поставку допустима по требованию пользователя; дефектом A2 была именно непреднамеренная подстановка клиента.

Проверено: backend Maven package с 65 тестами; frontend ESLint/55 tests/TypeScript+Vite build. На копии рабочей БД проверены разные клиент/владелец, обязательный default, переопределение владельца строки, подтверждение/UNLOAD_FINISH, CHANGE_OWNER до/после подтверждения вывоза, сохранение владельца завершённого вывоза, ранний возврат, запрет возврата без владельца, ручная смена владельца возврата, повтор событий без дублей. Все 43 таблицы до запуска сценариев на копии сохранили контрольные суммы. Схема БД не изменяется. Резервная копия: before-owner-source-2026-11-02.dump. ## Уточнение: собственник автоматически меняется только в черновике вывоза — 2026-11-02

Это уточнение заменяет прежнее правило синхронизации DRAFT/CONFIRMED. Только DRAFT получает актуальный собственник из container_owner при его изменении. При подтверждении вывоза owner_container_id фиксируется из регистра; после подтверждения ни CHANGE_OWNER, ни LOAD_FINISH не переписывают это поле. Для CONFIRMED/COMPLETED API показывает сохранённый owner_container_id, а не текущий регистр. Сам container_owner при CHANGE_OWNER меняется независимо от снимка подтверждённого вывоза; выполнение вывоза сохраняет актуального собственника регистра и меняет статус на DEPARTED.

Возврат по умолчанию копирует собственника вывоза: для DRAFT — актуальное значение регистра, для CONFIRMED/COMPLETED — зафиксированное значение заявки. Ручное редактирование собственника черновика возврата остаётся разрешённым.

Проверено: Maven package с тестами; сценарии API+SQL на отдельной копии БД для авто и ЖД, включая два вывоза одного КТК (подтверждённый сохраняет собственника, черновик обновляется), выполнение после CHANGE_OWNER и возврат из подтверждённого вывоза. Контрольные суммы 43 таблиц на копии до сценариев совпали с рабочей БД. Изменения схемы и корректировка существующих данных не требуются; frontend не пересобирается. Резервная копия before-draft-owner-2026-11-02.dump.
