# Учёт КТК и смена собственника

Реализовано 02.11.2026 по `docsforanalytics`: `container-remains-and-owner-as-is.md` (актуализация KIS-4830), `service-order-lifecycle.md`, `receiving-inbound-actions.md` и исходному backend. Для правил, появившихся после июльского архива, основание — новая документация, а не несуществующий в архиве код сентября–октября.

## Данные

- `service_order` — новый процесс `CHANGE_OWNER`, статусы `DRAFT`/`DONE`, новый собственник `client_id`, общий номер `number`, комментарий и `completion_at`.
- `service_order_container` — связи этой заявки с физическими КТК, уникальная пара заявка + КТК.
- `container_owner` — одна текущая запись на КТК: `client_id`, `status`, `receiving_order_id`, `shipping_order_id`.
- `container_owner_history` — неизменяемый через API журнал старого/нового собственника и состояния, КТК и заявки. Тип заявки: `RECEIVING_ORDER`, `SHIPPING_ORDER` либо `SERVICE_ORDER`.
- `container_movement` — ручные `UNLOAD_FINISH` и `LOAD_FINISH`, уникальные для заявки + КТК + события.
- `outbound_data` — локальная очередь `SERVICE_ORDER_CHAIN_PACKAGE`. При выполнении смены собственника создаётся одна запись, но внешняя интеграция и отправка не включены: адрес/учётные данные не заданы и отправка пользователем не запрошена.

`comprehensive_service_order` и ссылки `comprehensive_service_order_id` сохраняют процесс комплексной услуги и биллинг. Новый `service_order_id` относится только к смене собственника.

## Ручной приход/расход

Вместо TOS используется согласованный с пользователем локальный сценарий:

| Действие | Состояние регистра |
|---|---|
| Подтвердить поставку | Новый/выбывший КТК → `EXPECTED` |
| Завершить разгрузку | `UNLOAD_FINISH`, `EXPECTED` → `ON_TERMINAL`, заявка `COMPLETED` |
| Подтвердить вывоз | Только свободный `ON_TERMINAL` → `RESERVED_OUT` |
| Завершить погрузку | `LOAD_FINISH`, `RESERVED_OUT` → `DEPARTED`, заявка `COMPLETED` |

Ручное событие завершает все номерные КТК данной заявки одной транзакцией. Повтор события выполненной заявки не создаёт движений или начислений. Существующий `PATCH /status` при переходе в `COMPLETED` вызывает ту же логику учёта. Статус заявки остаётся `COMPLETED`: `UNLOAD_FINISH` — код события, не замена статуса.

Собственник поставки выбирается отдельно из клиентов. Для ЖД-поставки создаются строки `receiving_order_container` по уникальным КТК накладных; в карточке поставки на вкладке КТК можно выбрать собственников. Исходный `waybill_container.owner` остаётся строкой и не преобразуется в клиента по имени. Отдельный client-FK в накладную не добавлен, согласно прежнему решению пользователя.

Собственник вывоза не выбирается вручную: при создании/изменении черновика берётся из регистра, при подтверждении фиксируется актуальный снимок. Ранее передававшийся `ownerClientId` в запросе вывоза игнорируется. Приход и расход невозможны без соответствующего резерва именно этой заявки. Повторная поставка возможна после `DEPARTED`. Возврат создаёт новую поставку и проходит тот же цикл. Неизвестные/безномерные КТК не создают фиктивный номерной остаток.

Существующие статусы MVP не включают отмену, поэтому механика отмены заявок и обратных переходов из основной системы не добавлена. Прямого API редактирования регистра нет.

## Смена собственника

1. Создать черновик: новый собственник-клиент, `CHANGE_OWNER`, комментарий.
2. Выбрать записи `container_owner`: текущий собственник отличается от клиента заявки, КТК не занят другой DRAFT-заявкой на смену собственника. Состояние остатка не ограничивает эту операцию — как в описанном обработчике.
3. Можно менять комментарий/состав или удалить черновик; клиент заявки не меняется.
4. Выполнение блокирует заявку и физические КТК, меняет собственника без изменения состояния остатка, пишет историю только при фактической смене, ставит `DONE` и `completion_at`, добавляет локальный outbound. Всё в одной транзакции.
5. После `DONE` изменение, удаление и повторное выполнение запрещены (MVP возвращает 409 вместо исходного случайного 500).

В отличие от описанных гонок основной системы, выбор КТК разными черновиками сериализован блокировками физического КТК. Неверная замена состава не удаляет прежний выбор. Ошибки расчёта услуг откатывают движение и статус вместе с начислениями.

## API и UI

- `GET /api/container-owners` — регистр с фильтрами `query`, `clientId`, `status`, `page`, `size`.
- `GET /api/container-remains` — физические остатки (`ON_TERMINAL` и `RESERVED_OUT`), `inRemains=false` возвращает все состояния.
- `GET /api/containers/{id}/owner-history` — история выполненных заявок с итоговым `ON_TERMINAL`/`DEPARTED`; `includeReservations=true` показывает полный журнал.
- `POST /api/receiving-orders/{id}/events` с `{ "eventCode": "UNLOAD_FINISH" }`.
- `POST /api/shipping-orders/{id}/events` с `{ "eventCode": "LOAD_FINISH" }`.
- `GET/POST /api/service-orders`, `GET/PUT/DELETE /api/service-orders/{id}`.
- `GET /api/service-orders/{id}/containers/available` — подбор КТК с поиском и пагинацией.
- `PUT /api/service-orders/{id}/containers` — список `{containerOwnerId}` для нового выбора либо `{id}` существующей связи. Пустой список очищает состав; дубли сворачиваются.
- `POST /api/service-orders/{id}/accept` — выполнить смену собственника.

В меню: «Отчеты → Остатки и собственники КТК», «Заявки → Смена собственника КТК». Комплексные услуги находятся в своём реестре. Ручные кнопки «Завершить разгрузку» и «Завершить погрузку» доступны после подтверждения поставки/вывоза.

## Собственник КТК по умолчанию · 02.11.2026

По новой документации defaultContainerOwner у ReceivingOrder ссылается на Client: физическое поле receiving_order.default_container_owner_id. В MVP API — defaultContainerOwnerId, в ответе также defaultContainerOwnerName. При отсутствии поля берётся клиент заявки. При создании/обновлении строки КТК без ownerClientId используется собственник заявки по умолчанию; явно заданный собственник строки сохраняется. Для ЖД-поставки он сразу заполняется во всех receiving_order_container, исходный текст владельца в накладной остаётся независимым. В создании comprehensive_service_order поле передаётся в дочернюю поставку, на корне комплексной услуги не хранится.

Уточнённое пользователем правило: смена defaultContainerOwnerId в черновике заменяет собственников ВСЕХ КТК заявки, включая явно назначенных. Повторная передача того же default не сбрасывает индивидуальные значения. Массовая смена и сохранение реквизитов выполняются в одной транзакции PATCH /api/receiving-orders/{id}/containers (containers может быть пустым, если передан defaultContainerOwnerId). В подтверждённой/выполненной поставке менять поле нельзя; регистр/история при изменении черновика не затрагиваются. После подтверждения в container_owner попадают уже разрешённые собственники строк. Вывоз по-прежнему использует только регистр, defaultContainerOwnerId в его API отклоняется.

Форма создания поставки/комплексной заявки и карточка черновика показывают поле «Собственник КТК по умолчанию». При смене клиента в создании значение сбрасывается на нового клиента. Миграция V6 добавляет поле без удаления данных; существующим поставкам ставится их client_id, и только пустые собственники КТК существующих черновиков дозаполняются этим значением. Существующие регистр и история не переписываются.

Проверено: Maven package с тестами на кэшированных зависимостях (offline), frontend ESLint/58 tests/build, scripts/default-owner-smoke-test.mjs на отдельной БД billing_default_owner_test / 127.0.0.1:8087. Обычный Dockerfile проекта не изменён; из-за недоступности Docker Hub тестовые образы собраны из локальных ранее проверенных базовых слоёв.


## Только номерные заявки — 2026-11-02

По уточнённому решению пользователя исключены все безномерные и смешанные режимы, включая RAILWAY_CARRIAGE, CONTAINER, NONE и VEHICLE_UNNUMBERED. Для авто требуется номер каждого КТК; для ЖД-вывоза — номер каждого вагона и каждого КТК в вагоне. Приём по ЖД допускается только по накладным, в каждой из которых есть вагоны с номерными КТК. У всех заявок fillingType=ALL (значение по умолчанию при отсутствии поля).

UI больше не предлагает выбор режима и количественные строки. API отвергает старые режимы и непустые containerQuantities/railwayCarriageQuantities с HTTP 400 NUMBERED_COMPOSITION_REQUIRED. Старые значения enum сохранены только для явного отказа старым клиентам; количественные поля DTO остаются пустыми в ответах для совместимости. V7 ограничивает shipping_order.filling_type значением ALL и удаляет три пустые таблицы: shipping_order_railway_carriage_qty, shipping_order_container_qty, shipping_order_etsng_code. При обнаружении данных старых режимов миграция прерывается вместо удаления заявок. V1–V6 не изменены.

Проверено: backend Maven package с тестами; frontend ESLint, 55 тестов, TypeScript/Vite build; 27 API/SQL-сценариев на копии БД, включая отказ всех старых режимов на обоих транспортах и ресурсах, обход через ALL+количество, номерные авто/ЖД, откат создания поставки с неполной накладной и CHECK БД. Контрольные суммы данных всех 43 оставшихся таблиц до/после V7 совпали на копии. Перед применением создана резервная копия before-numbered-only-2026-11-02.dump. Аудит A6 закрыт исключением функционала, остальные замечания аудита этим изменением не исправляются.


## Собственник КТК независимо от клиента — уточнение 2026-11-02

Обычный client_id заявки на поставку/вывоз не определяет собственника регистра. При создании поставки defaultContainerOwnerId обязателен и выбирается независимо от клиента; неуказанный собственник строки подставляется из этого поля, явный собственник строки имеет приоритет. В черновике можно менять собственника отдельного КТК; изменение общего собственника по умолчанию по ранее принятому правилу обновляет все строки. Смена клиента/транспорта формы не заменяет отдельно выбранного собственника. Старые сохранённые владельцы и данные не переписываются.

При подтверждении поставки container_owner.client_id получает собственника соответствующей строки receiving_order_container (статус EXPECTED). UNLOAD_FINISH переводит КТК в ON_TERMINAL с сохранением собственника регистра. CHANGE_OWNER изменяет собственника регистра; DRAFT/CONFIRMED вывозы получают актуального собственника из container_owner по container_id. Изменение регистра синхронизирует owner_container_id активных вывозов в той же транзакции. Завершённый вывоз хранит собственника на момент LOAD_FINISH и не меняется задним числом.

По отдельному уточнению пользователя возврат допускает ручной выбор собственника. При создании собственник каждого КТК копируется из вывоза: для активного вывоза это актуальный регистр, для завершённого — сохранённый собственник на момент вывоза. Общий default возврата устанавливается по первому КТК; у всех строк сохраняются их собственные значения. Если собственника в вывозе ещё нет (исходная поставка не подтверждена), создание возврата возвращает HTTP 409 RETURN_OWNER_REQUIRED без записи возврата. Подстановка клиента исключена. Ручное изменение владельца в черновике возврата разрешено; при подтверждении такой возврат регистрирует выбранного владельца. Поэтому смена владельца через явно отредактированную входящую поставку допустима по требованию пользователя; дефектом A2 была именно непреднамеренная подстановка клиента.

Проверено: backend Maven package с 65 тестами; frontend ESLint/55 tests/TypeScript+Vite build. На копии рабочей БД проверены разные клиент/владелец, обязательный default, переопределение владельца строки, подтверждение/UNLOAD_FINISH, CHANGE_OWNER до/после подтверждения вывоза, сохранение владельца завершённого вывоза, ранний возврат, запрет возврата без владельца, ручная смена владельца возврата, повтор событий без дублей. Все 43 таблицы до запуска сценариев на копии сохранили контрольные суммы. Схема БД не изменяется. Резервная копия: before-owner-source-2026-11-02.dump. A2 закрыт; остальные замечания аудита этой работой не исправлялись.


## Уточнение: собственник автоматически меняется только в черновике вывоза — 2026-11-02

Это уточнение заменяет прежнее правило синхронизации DRAFT/CONFIRMED. Только DRAFT получает актуальный собственник из container_owner при его изменении. При подтверждении вывоза owner_container_id фиксируется из регистра; после подтверждения ни CHANGE_OWNER, ни LOAD_FINISH не переписывают это поле. Для CONFIRMED/COMPLETED API показывает сохранённый owner_container_id, а не текущий регистр. Сам container_owner при CHANGE_OWNER меняется независимо от снимка подтверждённого вывоза; выполнение вывоза сохраняет актуального собственника регистра и меняет статус на DEPARTED.

Возврат по умолчанию копирует собственника вывоза: для DRAFT — актуальное значение регистра, для CONFIRMED/COMPLETED — зафиксированное значение заявки. Ручное редактирование собственника черновика возврата остаётся разрешённым.

Проверено: Maven package с тестами; сценарии API+SQL на отдельной копии БД для авто и ЖД, включая два вывоза одного КТК (подтверждённый сохраняет собственника, черновик обновляется), выполнение после CHANGE_OWNER и возврат из подтверждённого вывоза. Контрольные суммы 43 таблиц на копии до сценариев совпали с рабочей БД. Изменения схемы и корректировка существующих данных не требуются; frontend не пересобирается. Резервная копия before-draft-owner-2026-11-02.dump.


## Единая таблица КТК в поставке и вывозе — 2026-11-02

OrderContainerTable используется при ручном создании авто-поставки/вывоза, выборе КТК в вагонах ЖД-вывоза, предпросмотре КТК выбранных накладных ЖД-поставки, просмотре/редактировании всех этих заявок. В одной строке: №, номер КТК, собственник, номера ЗПУ, тип ЗПУ, класс опасности груза, порожний, текущий статус КТК. На узких экранах таблица прокручивается горизонтально. Убрано дублирование состава КТК и отдельной формы реквизитов; таблицы накладных, вагонов и грузов сохранены. Безномерные и произвольные КТК не добавлены. Excel-импорт и создание справочников из таблицы не добавлялись: запрос касается существующих полей и их представления.

По уточнению пользователя ручной вывоз автоматически получает только собственника из регистра при выборе номера; ЗПУ, класс опасности и признак порожнего задаются вручную. Собственник и статус показываются без возможности редактирования. POST /api/container-owners/lookup принимает до 1000 containerIds и возвращает собственника/статус по физическому КТК; несуществующие IDs возвращают 404, пустой список — 400. В поставке собственник строки выбирается отдельно из клиентов, пустое значение использует явно выбранный defaultContainerOwnerId. В ЖД-поставке по накладным при создании состав только просматривается; строковые реквизиты можно менять в черновике после сохранения, как раньше.

При автоматическом создании вывоза комплексной услуги реквизиты берутся из исходной поставки/накладных. Приоритет имеют заполненные реквизиты receiving_order_container; затем реквизиты накладной. Класс определяется через waybill_product.danger_product_id → danger_product.danger_class_id; при разных классах нескольких грузов и отсутствии выбранного класса в поставке единственный класс не выдумывается. Номера ЗПУ сохраняют ведущие нули. При создании ЖД-поставки однозначные ЗПУ/тип/класс копируются в receiving_order_container. V8 дозаполняет только пустые атрибуты черновиков ЖД-поставок и автоматических вывозов; существующие значения, собственники и подтверждённые/выполненные заявки не переписываются.

Правило собственника сохранено: shipping_order_container.owner_container_id автоматически обновляется только в DRAFT; CONFIRMED/COMPLETED используют снимок подтверждения. Новый containerStatus в ответе КТК — текущий статус регистра, а не статус заявки. Waybill.owner остаётся текстом, не используется как клиент-собственник заявки.

Проверено: Maven package с тестами; frontend ESLint/59 tests/TypeScript+Vite build; API/SQL-сценарии на изолированной копии (создание комплексной услуги, приём, CHANGE_OWNER, авто/ЖД-вывоз, возврат, ручное переопределение владельца возврата, lookup, ручной вывоз, автоперенос ЗПУ/типа/класса). В браузере проверены автоматический вывоз, ручная подстановка собственника без остальных реквизитов и смена собственника строки поставки. V8 на копии изменил только один ранее пустой danger_class_id автоматического черновика; остальные поля 43 таблиц сохранены. Резервная копия before-shipping-ktk-2026-11-02.dump. ## Добавление КТК в редактируемый черновик — 2026-11-02

По умолчанию ручная форма содержит одну строку КТК; сброс вида транспорта также оставляет одну строку. В новом вагоне ЖД-вывоза сразу появляется одна строка КТК. Номер КТК в общей таблице отображается обычным начертанием.

При редактировании ручных авто-поставок/вывозов и ручных ЖД-вывозов в DRAFT доступно «Добавить» в общей таблице. В ЖД-вывозе новые КТК добавляются к уже включённому вагону. Новые строки выбираются из справочника, порожние требуют только реквизиты КТК, гружёные — также груз по ЕТСНГ и положительную массу с точностью до 3 знаков. Можно убрать ещё не сохранённую строку; удаление существующих КТК этим изменением не добавлено. Собственник поставки выбирается отдельно с defaultContainerOwnerId; собственник вывоза только читается из регистра.

По явному ответу пользователя ограничения источника сохранены: в ЖД-поставках, заявках комплексной услуги и связанных возвратах прямое добавление запрещено, состав управляется источником. CONFIRMED/COMPLETED также не допускают добавления.

PATCH /api/{receiving-orders|shipping-orders}/{id}/containers расширен необязательным additions: [{ container: { containerId, empty, cargo, ownerClientId, sealNumbers, sealTypeId, hazardClassId, cargoItems? }, railwayCarriageId? }]. railwayCarriageId — ID справочника вагона, который уже присутствует в этой ЖД-заявке. Старые containers/defaultContainerOwnerId работают без изменений. Метаданные и новые строки сохраняются в общей транзакции; при ошибке откатываются и изменения старых реквизитов/общего собственника. Полный состав проверяется существующими OrderRequestValidator/ReferenceDataService: дубли, справочники, груз/масса, 1x40 либо до 2x20 для автовывоза, принадлежность вагону. Повторные/параллельные добавления одного КТК сериализуются блокировкой заявки и не создают дубли. При редактировании DRAFT регистр не пополняется до подтверждения поставки.

Проверено: Maven package с тестами; ESLint/64 frontend tests/TypeScript+Vite build. На копии БД проверены авто-поставка/вывоз, гружёные и порожние добавления, источники, подтверждённые заявки, дубли, некорректные справочники/вагон/груз, вместимость, откат метаданных/default, два конкурентных одинаковых запроса.
