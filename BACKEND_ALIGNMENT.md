Актуализировано **06.11.2026, V26**. Этот файл описывает текущий MVP, не обещания основной системы. Детальная история сопоставления с предоставленным backend и прежние решения сохранены в [архиве](docs/history/2026-11-03-handoff/BACKEND_ALIGNMENT.md).

Источник сверки основной системы — `docs/reference/docsforanalytics 2.zip`; ранее также анализировался предоставленный `backend.7z`. Интеграции из этих материалов не запускались. При конфликте сначала проверить реальную реализацию и последнее решение пользователя.

## Жизненный цикл поставок, вывозов и рейсов

1. Черновик транспортной заявки может быть без рейса, даты и отправителя/получателя; это необходимо для автосоздания.
2. Подтвердить поставку/вывоз можно **только через рейс**. Отдельная кнопка подтверждения в транспортной карточке отсутствует; прямой переход API также ограничен.
3. Подтверждение рейса требует хотя бы одну связанную заявку и DRAFT у всех заявок. У поставок обязательны дата/время поступления и грузоотправитель, у вывозов — дата/время вывоза и грузополучатель. Проверяется весь пакет; ошибка откатывает переход.
4. После подтверждения отдельные заявки выполняются кнопкой «Выполнить». Складские проверки и начисления входят в транзакцию перехода.
5. Когда все заявки рейса COMPLETED, подтверждённый рейс автоматически становится COMPLETED.
6. Комплексная заявка автоматически становится COMPLETED, когда все её поставки/вывозы завершены и все исходные КТК распределены в связанные вывозы. Не завершать её только по пустому набору созданных вывозов.

Основной код — `order/OrderStatusService.java`, `route/RouteService.java`, `containerstock/ContainerStockService.java`, `billing/BillingService.java`.

## Состав, накладные и массы

- КП-ЖД читает состав из накладных (`waybill_details`, `waybill_railway_carriage`, `waybill_container_details`, продукты/ЗПУ); не создавать второй независимый состав в `receiving_order_container`.
- КП-Авто использует `receiving_order_container` и items; вывоз — соответствующие shipping-таблицы.
- Доступны только свободные накладные. Совместимость станций отправления/назначения и плательщика проверяется сервером; выбор сохраняется между вкладками/страницами frontend.
- Один груз на накладную. Состав исходной накладной не редактируется через транспортную заявку; собственник КТК заявки допускает изменение по правилам черновика.
- Массы MVP — кг, точность0,001. `container.weight` — тара, `lifting_capacity` — грузоподъёмность; `waybill_container.weight` — брутто, `net_weight` — нетто. `wight_net` в item-таблицах — намеренно сохранённое имя исходной модели.
- `net_weight=0` соответствует порожнему КТК. Не изменять единицы и не подменять сохранённое нетто пересчётом по новым справочным значениям без задачи.
- Опасность/класс и ЗПУ ЖД-состава берутся из накладной; связанная классификация — `danger_product`/`danger_class`, ЗПУ — `waybill_zpu`.
- V11: `shipment_type=CONTAINER`, `status=IN_TRANSIT`; у старых записей `created_at` отсутствовала и остаётся NULL. Новые получают CURRENT_TIMESTAMP. Не выдумывать старые даты.

## Собственник и движение КТК

Клиент договора, грузоотправитель/получатель и собственник КТК — разные роли. Собственник не обязан совпадать с клиентом заявки.

В поставке выбирается `default_container_owner_id`; конкретный собственник может быть изменён для отдельного КТК. Для ЖД выбранное значение хранится в `waybill_container.owner_container_id`, а текстовый owner из ЭТРАН не является источником складского собственника. Для авто используется `receiving_order_container.owner_container_id`.

| Событие | Состояние КТК |
| --- | --- |
| Подтверждение поставки | EXPECTED |
| Выполнение поставки | ON_TERMINAL |
| Подтверждение вывоза | RESERVED_OUT; КТК должен быть свободен на терминале |
| Выполнение вывоза | DEPARTED |

Изменения фиксируются в истории. Собственник в черновых вывозах может актуализироваться из складского состояния; в подтверждённом/выполненном вывозе сохраняется зафиксированное значение.

Смена собственника — отдельная заявка `service_order`: только DRAFT («Черновик») и DONE («Выполнено»), минимум один выбранный КТК обязателен при создании и подтверждении. При «Подтвердить» перепроверяются состояние КТК и исходный собственник, затем изменение и история сохраняются транзакционно. Редактирование — только черновика.

## Комплексная заявка и возврат

При создании обязательны выбранная услуга, клиент, договор, совместимые свободные накладные и собственник КТК по умолчанию. Доступны два каталожных варианта сценария RAILWAY_RETURN: повагонный приём (1–39 КТК на каждой накладной) и приём в составе поезда (от 40). Пределы хранятся в каталоге, проверка на клиенте выполняется по «Далее» из вкладки «Накладные ЭТРАН» и повторяется сервером при создании. Название услуги не определяет поведение.

Создаётся исходная ЖД-поставка INITIAL_RECEIVING. Для каждого 40-футового КТК сразу создаются автовывоз и возвратная автопоставка RETURN_RECEIVING. 20-футовые КТК распределяются позже по одному или два на машину; создание вывоза сразу создаёт его возврат. Повторное распределение запрещено. Возвраты содержат порожние КТК и относятся к той же выбранной услуге.

ReturnReceivingService — внутренний сервис автоматического создания возврата; отдельных HTTP-команд одиночного/пакетного создания возвратов больше нет. Плановый собственник берётся из КТК исходной накладной, при отсутствии — из default owner поставки. Неоднозначность или отсутствие собственника откатывает всю операцию создания. Выполнение возврата разрешено только после выполнения его вывоза.

Прогресс возвращает одно serviceName, три этапа и их счётчики. Общая заявка завершается только после возврата всех исходных КТК, включая отложенные вывозы КТК20. Поставка Авто остаётся этапом выбранной услуги, самостоятельной автоуслуги нет.

## Редактирование дат и контрагентов

Дата поставки — `receiving_order.plan_receiving_date_time`, дата вывоза — `shipping_order.planned_shipping_date_time`. API полей формы использует LocalDateTime; не применять дополнительное преобразование UTC как к timestamp рейса.

Грузоотправитель/получатель выбираются из всей таблицы `client` через `GET /api/references/clients`, без тарифного ограничения. Backend принимает только существующее имя, канонизируя регистр/пробелы; произвольный ввод отклоняется400 `CARGO_PARTY_CLIENT_NOT_FOUND`. При этом:

- `receiving_order.consignor` остаётся строкой.
- `shipping_order.consignee_id` остаётся FK на `client_related_entity`, а не на client.
- `PartyReferences.clientParty` создаёт/разрешает служебное представление выбранного клиента; новые записи скрыты из каталога перевозчиков (`transport_catalog_archived=true`, `active=false`).

Последнее явное заполнение данных добавило ПАО «СИБУР Холдинг», ООО «Смартлог», ПАО «ТрансКонтейнер» и исправило15 существующих транспортных заявок. Остальные роли/даты/статусы не менялись; ИНН и контакты не выдумывались. Скрипт `client-parties-demo.sql` не запускается автоматически.

`PATCH /api/comprehensive-service-orders/{id}/transport-metadata` принимает:

```json
{"orders":[{"id":"UUID","kind":"SHIPPING или RETURN_RECEIVING","plannedAt":null,"partyName":null,"originalPlannedAt":null,"originalPartyName":null}]}
```

Проверяются принадлежность, DRAFT, возвратная роль, дубли, длина имени, исходные дата/контрагент. Родитель и документы блокируются; весь пакет сохраняется либо откатывается. При конфликте нужно отменить редактирование и открыть заново. Начальные поставки этим endpoint не редактируются. Отдельные транспортные карточки сохраняют метаданные через `PATCH .../{id}/containers`.

## Логистика рейса

Каталоги `/api/transport-catalogs/{carriers|drivers|vehicles}`: список (опционально activeOnly), карточка, создание, редактирование и удаление с защитой используемых связей.

| Источник | Реквизиты |
| --- | --- |
| `client_related_entity` | Перевозчик/экспедитор, name, active, transport_catalog_archived |
| `client_driver` | ФИО в code, active, phone_number, poa_number, poa_valid_to |
| `client_vehicle` | Госномер в code, active, insurance_number, with_trailer, trailer_number |

У авто обязательны три выбранные активные записи. В редактируемом DRAFT допускается сохранить ранее выбранную неактивную, но нельзя назначить новую неактивную. Для ЖД автологистика отсутствует. Телефон/доверенность берутся из водителя, страховка/прицеп — из ТС; реквизиты читаются из справочников, отдельного неизменяемого снимка рейса нет.

Телефон нормализованного вида +7 и10 цифр, госномера РФ нормализуются с учётом похожих латинских букв, регионы2/3 цифры. При with_trailer=true номер прицепа обязателен; иначе он пуст. NULL у старых записей означает отсутствие сведений, а не выдуманное «нет».

V18 добавила реквизиты, отдельный одноразовый script создал12 записей каждого вида и назначил их существующим8 авторейсам;2 ЖД-рейса без автологистики. V19 скрыла ранее использовавшиеся как грузополучатели старые записи перевозчиков, сохранив связи. Транспортные каталоги не являются автоматически полным списком клиентов.

Рейс редактируется в DRAFT, вкладки Основное/Заявки. PUT `/api/routes/{id}` сохраняет дату, логистику, комментарий и добавляемые заявки с серверной проверкой совместимости. Дата отображается как интервал data_time→+1час в UTC+3, включая дату окончания при переходе полуночи.

## Тарифы и начисления

`complex_service_tariff.active` (V12) управляет доступностью тарифа для новых заявок. Для услуги+клиента+договора разрешён один активный тариф (частичный уникальный индекс). Если активный уже существует, новая запись по этому ключу не создаётся; сначала прежнюю нужно отключить. Активация конкурирующей записи запрещена. Изменение active — через форму, не checkbox таблицы. Использованный тариф нельзя удалить.

При создании заявки нужен **один активный тариф выбранной услуги** для клиента и договора. Единственный снимок в comprehensive_service_order_tariff содержит исходный тариф, коэффициент, базовые и рассчитанные цены с/без НДС. Изменение, отключение или переименование тарифа/услуги не меняет сохранённый расчёт.

BillingService фиксирует количество принятых КТК при выполнении ЖД-поставки; при выполнении вывоза проверяет завершение исходной поставки. Начисление появляется только при выполнении возврата: одна запись service_execution на заявку+КТК, цена строго из снимка заявки, одна billing_charge на исполнение. Отсутствующий снимок — ошибка с откатом всей операции, подбора текущего тарифа нет. Повторные и конкурентные команды выполнения не создают дублей.

V26 удаляет старое деление А/Б: purpose в каталоге/снимках, family и неиспользуемый accepted_container_count в исполнении, a_complex_service_id в поставке. Поле accepted_container_count исходной поставки и acceptance_fixed_at сохраняются для фактического приёма. selected_complex_service_id обязателен. Автоуслуга и её неиспользованные тарифы удалены. Миграция блокируется при старых заявках без выбранной услуги/снимка или исторических исполнениях прежней схемы; финансовая история автоматически не переосмысливается.

## Счета

Создание по клиенту, договору и месяцу оказания; границы периода — Europe/Moscow. КТК — необязательный множественный UI-фильтр списка доступных начислений. Одна оказанная услуга — отдельная строка; начисления, занятые другими счетами, включая черновики, недоступны.

После создания счёт DRAFT, название «Счёт №…». Состав и суммы сохраняются, новые начисления сами не добавляются. DRAFT редактируется через карандаш, удаляется из строки реестра. «Оплачен» переводит в PAID; редактирование/удаление оплаченного запрещено. Version защищает update/paid от устаревшей вкладки. Выбор начислений и ограничения повторно проверяет backend.

В счёте есть ссылка на одну общую карточку тарифа `/complex-services/tariffs/{tariffId}`. В ней не перечисляются счета, КТК и заявки как будто тариф принадлежит одной строке. Endpoint применённого тарифа в счёте сохраняется для получения сведений о расчёте.

Не все реквизиты просмотра автоматически являются редактируемыми через metadata endpoint.

Интеграций TOS/Datareon/1С/ЭТРАН и полного аудита/документооборота основной системы нет. Исторические даты/тарифы/реквизиты не восстанавливать догадками. Тестовые наполнения и операции перенумерации не являются автоматическим seed приложения.

## Типы ЗПУ после V21

waybill_zpu.zpu_type — UUID FK на seal_type.id с ON DELETE RESTRICT; название читается через JOIN по UUID. Поставки и вывозы используют тот же seal_type через свои seal_type_id. Сервер проверяет принадлежность договора клиенту, КТК вывозу и отсутствие повторного возврата. Блокировка исходной услуги/вывоза и уникальный индекс `(source_shipping_order_id,container_id)` защищают также конкурентные запросы.

V27 из `db/baseline`: `comprehensive_service_order.workflow/source_service_order_id`, связь источника в `receiving_order_container`, ослабление старых составных FK в пользу отдельных FK для межклиентского возврата; проверка клиент/договор родительской заявки сохраняется. Существующая запись автоуслуги определяется стабильным UUID, её название и цены не перезаписываются. Если записи нет (например, восстановлен V26-снимок), миграция добавляет её без тарифов. Старое разделение тарифов А/Б не возвращается.

## 06.11.2026 — массовый возврат из карточки услуги

Актуальное уточнение ручного возврата: кнопка «Создать возврат» находится **над таблицей на вкладке «Заявки на вывоз - Авто»**, рядом с действиями раздела. Форма показывает все КТК, уже включённые в вывозы этой услуги и ещё не включённые в возврат, с номером исходного вывоза. Есть отдельные флажки и «Выбрать все» с промежуточным состоянием; изначально массовый выбор пуст.

На каждый выбранный КТК создаётся **отдельная возвратная поставка**, даже если два КТК находятся в одном вывозе. Клиент/договор выбирается один раз для всего набора. Для исходной пары все возвраты входят в исходную услугу; для другой пары создаётся **одна новая автоуслуга на весь набор**, с единым снимком тарифа и всеми созданными возвратами. Следующее самостоятельное оформление на другую пару создаёт свой отдельный набор/автоуслугу; существующие автоуслуги автоматически не объединяются.

Весь набор создаётся одной транзакцией. Недоступный КТК, дубли, отсутствующий собственник или тариф отменяют всю операцию без частичных документов. Одновременные повторные запросы сериализуются блокировкой исходной услуги; после успешного запроса повтор получает409. После создания UI обновляет прогресс и возвраты, показывает их количество и ссылку на автоуслугу. Действие в отдельной карточке вывоза также использует общее правило «один КТК — одна возвратная заявка».

API: `GET /api/comprehensive-service-orders/{id}/returns/available-containers`; `POST /api/comprehensive-service-orders/{id}/returns` с `containerIds` (1–10000 уникальных UUID), `useCurrentClient`, `clientId/contractId`. Ответ: `serviceOrderId`, `serviceOrderCode`, `createdService`, `returns` — список созданных заявок. Старый POST для отдельного вывоза допускает ровно один КТК; интерфейс использует новый массовый API. Схема V27 без новых миграций. Рабочие данные не очищались и не изменялись проверками.
